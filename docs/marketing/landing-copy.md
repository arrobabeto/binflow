## El dolor (problema)

**Section label:** El problema de siempre

**Headline:**  
Actualizar la web no debería costar una semana ni tres personas.

**Body:**  
Cada artículo, cada ajuste, cada “¿puedes subir esto?” se convierte en mensajes, tickets, borradores perdidos y revisiones eternas. El cliente no quiere aprender otra herramienta. El equipo no quiere ser el cuello de botella. Y la IA genérica escribe bonito… pero no sabe las reglas de *tu* web.

**Pain bullets:**

1. **Demasiadas manos en un cambio simple** — briefing, redacción, diseño, subida, revisión, publicación.  
2. **El cliente no ve el resultado hasta tarde** — y cuando lo ve, ya se gastó tiempo.  
3. **La IA suelta no es operable** — inventa, duplica temas o rompe el estilo de marca.  
4. **Nadie sabe cuánto cuesta cada pedido** — horas humanas + tokens + idas y vueltas invisibles.  
5. **Publicar da miedo** — porque “subir a producción” sigue sintiéndose irreversible.

## Stacks soportados

**Section label:** Tu stack, listo

**Headline:**  
La misma experiencia de IA. El backend de contenido que ya elegiste.

**Intro:**  
No te pedimos migrar tu web a “la plataforma de Binflow”. Conectamos la IA al modelo con el que ya construyes y publicas.

### Stack cards (presentar como disponibles)

**Astro (sitio en repositorio)**  
Ideal para sitios modernos donde el contenido vive junto al código. La IA genera piezas (blog, casos, assets) y las publica con preview real antes de salir en vivo. Perfecto para portfolios, marcas y webs de alto rendimiento.

**Astro + Orbitype (CMS)**  
Astro en el frente, Orbitype como cerebro de contenido. La IA escribe y actualiza en el CMS, mantiene el espejo del sitio y te da preview exacto. Lo mejor de un sitio estático con la agilidad de un CMS.

**Nuxt (Vue) + Orbitype**  
Para productos y marcas en el ecosistema Vue/Nuxt. Misma promesa: pedir por chat, generar con IA, revisar preview y publicar — con Orbitype como fuente de contenido y Nuxt como experiencia.

**Astro + WordPress headless**  
WordPress como CMS headless; Astro como vitrina. El cliente no pelea con el admin clásico: pide en lenguaje natural, la IA opera el contenido en WordPress y el sitio Astro muestra el resultado con preview antes de publicar.

**WordPress**  
Para webs que viven en WordPress de punta a punta. La IA crea y actualiza entradas, medios y cambios permitidos con el mismo ritual: plan → generación → preview → aprobación → publicación. Menos dependencia del “que lo suba el developer”.

**Cierre de sección:**  
Un cliente, un stack. Varias cuentas, varios stacks. La IA se adapta; tu operación se estandariza.

**Nota de diseño:** Mostrar logos Astro / Nuxt-Vue / Orbitype / WordPress en fila o en cards iguales. No marcar ninguno como “próximamente”.

## Tools (capacidades)

**Section label:** Tools impulsadas por IA

**Headline:**  
Herramientas concretas. No un cajón de “hazme algo”.

**Intro:**  
Binflow no abre un chat infinito sin límites. Activa *tools* — operaciones claras que la IA puede ejecutar de punta a punta según el stack del proyecto, con preview y aprobación.

### Tool cards (copy sugerido)

**Crear artículo de blog**  
De un tema (o un borrador) a un artículo listo, con portada, metadatos y versión en otro idioma — en Astro, Orbitype o WordPress según el proyecto. Preview real. Publicación con un sí.

**Crear caso / proyecto**  
Convierte un brief en una pieza de portafolio estructurada, con evidencia y estilo de marca.

**Editar texto en página**  
Ajustes puntuales en landings y páginas CMS — sin rehacer todo el sitio.

**Editar imagen**  
Cambia o regenera visuales dentro de las reglas del proyecto y del CMS conectado, con preview antes de publicar.

**Editar estilo de texto**  
Afinaciones de tono y presentación sin perder la estructura aprobada.

**Actualizar menú**  
Ordena navegación y CTAs del sitio cuando el stack lo permite — con plan claro antes de tocar producción.

**Ticket / pedido fuera de catálogo**  
Cuando no cabe en una tool, el pedido llega ordenado al equipo — no se pierde en un chat eterno.

**Nota de diseño:** Mostrar solo las tools que quieras destacar en la primera pantalla; el resto puede ir en “Y más operaciones según el stack y el proyecto”.

**Cierre de sección:**  
Cada proyecto ve solo las tools de su stack. Menos ruido. Más claridad.

## Flow completo: del sitio al deploy

**Section label:** De cero a publicado

**Headline:**  
Primero conectas tu web. Después la IA opera. Tú solo apruebas.

**Intro:**  
Binflow no “sube archivos a ciegas”. Para publicar de verdad necesita el mismo camino que ya usas para desplegar: tu repositorio en GitHub, tu hosting de preview/producción y las reglas del proyecto. Una vez configurado, cada request sigue un flow claro hasta el deploy.

**Callout (destacado visual):**  
**GitHub es el puente al deploy.**  
Sin conexión al repositorio del sitio, la IA puede ayudar a redactar — pero no puede dejar el cambio listo para preview ni publicación. Con GitHub conectado, cada aprobación puede convertirse en un deploy real.

### Parte A — Cómo se configura un sitio (onboarding)

**Subheadline:**  
Se hace una vez por proyecto. Después, el cliente solo habla por chat.

**Flow horizontal o vertical (pasos numerados):**

```text
1. Crear el proyecto
   → 2. Elegir el stack
   → 3. Conectar GitHub
   → 4. Conectar deploy (preview + producción)
   → 5. Conectar IA
   → 6. Conectar chat del cliente
   → 7. (Si aplica) Conectar CMS
   → 8. Activar tools
   → 9. Sitio listo
```

**Copy por paso:**

1. **Crear el proyecto**  
   Das de alta la cuenta/cliente y el sitio que Binflow va a operar.

2. **Elegir el stack**  
   Astro, Astro + Orbitype, Nuxt + Orbitype, Astro + WordPress headless o WordPress. Esto define cómo publica la IA.

3. **Conectar GitHub**  
   Vinculas el repositorio del sitio. Aquí viven los cambios versionados. **Es el requisito clave para que un request pueda llegar a deploy.**

4. **Conectar deploy (preview + producción)**  
   Conectas el entorno donde se construye el preview y donde sale lo publicado (por ejemplo Vercel). Así el cliente ve el resultado real antes del sí final.

5. **Conectar la IA**  
   La clave de generación queda asociada a ese cliente. Cada pedido tiene costo visible.

6. **Conectar el chat del cliente**  
   Se empareja el bot de Telegram. Desde ahí pedirá, revisará y aprobará.

7. **Conectar el CMS (si el stack lo usa)**  
   Orbitype o WordPress, según el caso. La IA escribe donde ya guarda el contenido.

8. **Activar tools**  
   Eliges qué puede hacer ese sitio: blog, portafolio, editar texto, editar imagen, etc. Nada más.

9. **Sitio listo**  
   Validaciones en verde. El cliente recibe acceso. A partir de aquí empieza el flow de cada request.

**Microcopy bajo el flow de setup:**  
Configura el equipo una vez. El cliente no toca GitHub ni el panel de deploy.

**Nota de diseño:**  
Mostrar GitHub con énfasis (icono más grande / paso “clave”). Deploy y GitHub pueden ir enlazados visualmente (“sin esto, no hay publicación automática”).

### Parte B — De un request al deploy

**Subheadline:**  
Lo que pasa cada vez que alguien pide un cambio.

**Flow principal (timeline / stepper):**

```text
Request
  → Plan
  → Generación IA
  → Cambio en GitHub
  → Preview deploy
  → Revisión humana
  → Aprobación
  → Deploy a producción
  → Verificación + aviso
```

**Copy por etapa:**

1. **Request**  
   El cliente escribe en el chat o elige una tool. Nace un pedido con historial.

2. **Plan**  
   La IA interpreta y propone qué va a hacer. El humano confirma antes de gastar ciclo.

3. **Generación con IA**  
   Se crea el contenido, assets y estructura según las reglas del sitio.

4. **Cambio en GitHub**  
   El resultado se deja en el repositorio conectado (rama/borrador aislado). Aquí el request “toca tierra” en tu stack real.

5. **Preview deploy**  
   Se dispara un deploy de preview. El cliente abre el enlace y ve la web como quedaría.

6. **Revisión**  
   Aprueba, pide ajustes o cancela. Si pide revisión, se vuelve a generar/ajustar sin perder el hilo.

7. **Aprobación**  
   El sí queda atado a *ese* preview — no a una promesa abstracta.

8. **Deploy a producción**  
   Con la aprobación, Binflow publica por el mismo camino conectado (GitHub → deploy). Lo que viste es lo que sale.

9. **Verificación y aviso**  
   Se confirma que quedó en vivo y se notifica a cliente y equipo.

**Variante corta para UI compacta (5 nodos):**

| Nodo | Label | Hint |
| --- | --- | --- |
| 1 | Pedido | Chat / tool |
| 2 | IA | Plan + generación |
| 3 | GitHub | Cambio versionado |
| 4 | Preview | Deploy de prueba |
| 5 | Producción | Deploy tras aprobación |

**Frase punch del flow:**  
Del mensaje al aire: con GitHub conectado, preview real y un sí consciente.

## Objeciones / FAQ corto

**¿Reemplaza a mi equipo?**  
No. Elimina el trabajo mecánico de operar la web para cambios repetibles. Tu equipo se queda con estrategia, diseño alto impacto y excepciones.

**¿El cliente puede romper el sitio?**  
No. Solo puede usar las tools activadas y publicar lo que el flujo permite tras preview y aprobación.

**¿Y si la IA se equivoca?**  
Por eso existe el preview y la revisión. Nada sale en vivo sin un sí consciente.

**¿Cuánto cuesta?**  
Modelo privado por invitación. El valor está en menos horas de coordinación + costos de IA visibles por pedido. Hablemos de tu volumen.

**¿Necesito aprender otra plataforma compleja?**  
El cliente vive en el chat. El equipo opera desde un panel claro. La complejidad se queda detrás.

**¿Tengo que cambiar de stack?**  
No. Si estás en Astro, Nuxt + Orbitype, Astro + WordPress headless o WordPress, Binflow se adapta a ti.

**¿Orbitype y WordPress a la vez en la agencia?**  
Sí. Cada proyecto declara su stack. La experiencia del cliente (chat → preview → aprobar) se siente igual.

## Guía rápida para el agente de Figma

1. Primera pantalla: marca + headline + una frase + CTAs + atmósfera de producto (chat → preview → publish).  
2. Evitar dashboard genérico como héroe; preferir narrativa de conversación + resultado publicado.  
3. Secciones en este orden sugerido: Hero → Dolor → Promesa → **Stacks** → Para quién → Beneficios → Tools → Conexiones → Flujo rápido → **Flow completo (setup + request→deploy)** → Métricas → Confianza → CTA.  
4. En Stacks: 5 cards al mismo nivel visual (Astro repo, Astro+Orbitype, Nuxt+Orbitype, Astro+WP headless, WordPress). Ninguna como “coming soon”.  
5. En Tools y Conexiones: cards simples, una idea por card; logos de stack en Conexiones.  
6. En Flow completo: dos carriles (Setup una vez / Request cada vez). Resaltar **GitHub** como puente obligatorio al deploy. Usar stepper o timeline, no un dashboard denso.  
7. Métricas: números como placeholders editables; claims de “cero sorpresas / aislamiento” pueden ir firmes.  
8. Tono: premium operativo, no sci-fi púrpura ni “AI magic”.
